# 專案檔案整理設計規格

> 本文件描述 `D:\democase` 與 `D:\democase\ai` 的低風險整理方式。整理原則是保留重要資料、先分類與建立索引，不直接刪除使用者檔案。

## 1. 目標

將目前混合了 Flask 程式碼、正式文件、AI 對話產物、學校參考資料、BMAD 設定與執行快取的專案，整理成容易理解且不會破壞現有程式路徑的結構。

整理完成後，使用者應能快速回答：

- 哪些檔案是正式規格？
- 哪些 Markdown 是需求、計畫、日誌或歷史紀錄？
- 哪些檔案是程式碼與測試？
- 哪些檔案是學校參考資料？
- 哪些檔案只是 AI 工作暫存或產出物？
- 哪些資料可以重新產生，哪些資料必須保留？

## 2. 不變更的原則

- 不刪除舊文件、舊圖片、舊程式碼、AI 產出物或學校參考資料。
- 不執行 `git reset`、`git checkout`、強制清除或覆寫使用者既有變更。
- 不將 `.env`、密碼、Token 或其他機密資料寫入索引與公開文件。
- 不任意搬移 `app/`、`tests/`、`scripts/`、`run.py`、`requirements.txt`，避免破壞 Python 匯入與執行路徑。
- 不將 `.venv`、`__pycache__`、`.pytest_cache`、logs 視為正式程式碼或正式文件。
- 所有有可能影響既有連結的搬移，先建立對照表，再執行驗證。

## 5. 執行階段

### 階段一：建立索引

- 建立 `ai/docs/README.md`。
- 為每份 Markdown 記錄分類、用途、目前狀態與是否為建議閱讀文件。
- 建立 `ai/README.md` 的目錄說明，讓新對話或新開發者知道從哪裡開始。
- 不搬移檔案，先確保索引與實際路徑一致。

### 階段二：低風險分類

- 將 AI 工作產物整理至 `ai/archive/codex-sessions`，保留原本日期與檔名。
- 將明確屬於舊版或不宜直接使用的文件與圖表移入 `archive`，但保留原始內容。
- 先檢查是否有 Markdown、程式或報告引用原路徑，再進行搬移。
- 對每次搬移建立來源路徑與新路徑對照表。

### 階段三：程式與環境說明

- 保留 `app/`、`tests/`、`scripts/` 的現有路徑。
- 補充虛擬環境、測試、啟動 Flask 與 MySQL 的正確操作說明。
- 明確標示 `.venv`、`__pycache__`、`.pytest_cache`、`logs` 為本機產物。
- 檢查 `.gitignore` 是否涵蓋所有可重新產生的本機資料，但不隨意忽略需要保留的文件。

### 階段四：驗證

- 檢查所有索引連結與搬移後路徑。
- 在 `D:\democase\ai` 的虛擬環境中執行測試。
- 驗證 `python run.py` 能正常啟動，或至少能建立 Flask App。
- 確認 Git 工作區中的既有修改仍存在，沒有被清除或覆寫。
- 將無法驗證的外部服務、MySQL 連線或 Google 文件操作明確標註為待確認。

## 6. 風險與處理方式

| 風險 | 處理方式 |
|---|---|
| 搬移文件造成連結失效 | 先建立引用清單與路徑對照表，完成後搜尋舊路徑 |
| 誤刪使用者工作檔 | 不使用刪除指令，改採封存目錄 |
| 破壞 Python 匯入 | 不搬移 `app/`、測試與入口檔 |
| 把機密寫入索引 | 索引只記錄檔名與用途，不複製 `.env` 內容 |
| 混淆新版與舊版文件 | 用 `canonical`、`planning`、`archive` 分類並在索引標示狀態 |
| 現有未提交修改被覆蓋 | 整理前後檢查 Git 狀態，不進行 reset 或 checkout |

## 7. 完成標準

- 有一份可讀的 `ai/docs/README.md` 文件索引。
- 每份重要 Markdown 都有明確分類與用途。
- AI 工作產物與正式專案內容分開。
- 正式程式碼路徑維持可執行。
- 測試與 Flask App 驗證結果有實際命令輸出支持。
- 沒有刪除重要文件，也沒有遺失既有未提交變更。
