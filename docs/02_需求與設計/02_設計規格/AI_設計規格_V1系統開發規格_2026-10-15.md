## 1. 一句話目標

**把有限的開發時間，留給 Google 不會替我們做的事。**

V1 只做一條完整、能展示、能驗收的學生主線：

```
上傳證明 → OCR 辨識 → 學生確認 → 學習證據 → 有依據的自傳 → 導師確認送審版
```

不自己做文件編輯器、雲端硬碟、Email、行事曆、試算表、GPU AI 主機。

---

## 2. 角色（V1 只有 4 種）

| 角色 | 登入後要做的事 |
|---|---|
| 學生 | 看五年路線、上傳證明、確認 OCR 結果、看缺件、寫自傳、送審 |
| 班導師 | 看本班進度、在自傳上留意見、確認送審版 |
| 科辦／行政 | 電子證明、公告、表單 |
| 系統管理員 | 帳號、規則、資料來源、AI 設定、操作紀錄 |

專任教師、專題指導老師：V1 不另開角色，資料表保留關係欄位，之後有需要再開。

---

## 3. 系統架構

```
學生／班導／科辦／管理員
        │
   Flask 後端（總指揮：權限、規則、工作調度）
        │
 ┌──────┼───────────┬──────────┬────────────┐
MySQL   檔案存放       OCR        AI（Gemini）
正式資料  原始附件      圖片→文字    整理建議
        （先本機，      不做最終判定  只拿必要欄位
         之後換 Drive）
```

**三條原則**
1. **MySQL 是正式資料的來源**；檔案存放區只放原始附件。
2. **AI 和 OCR 都是被後端叫來做事的工具**，不直接讀整個雲端硬碟，也不做最終判定。
3. **檔案存放要做成可替換的**：V1 先存在伺服器本機；Google Drive 串接通過測試後，換成 Drive，其他程式不用改。

## 4. 主線功能與驗收條件

狀態說明：✅ 已完成（有程式和測試）｜🟡 有但是模擬的或部分完成｜⬜ 還沒做（2026-10-27 依程式重新核對；實機驗收另見第 10 節）

| # | 功能 | 驗收條件（做到才算完成） | 現在狀態 |
|---|---|---|---|
| M1 | 登入與 4 種角色權限 | 每個角色只看得到自己該看的；學生看不到別人的資料；導師只看得到本班 | ✅ |
| M2 | 五年路線首頁 | 新生第一次登入有引導；看得到五年進度、今天先做哪一步、學期照片拼圖 | ✅ |
| M3 | 上傳證明 | 學生上傳成績單／證照圖片或 PDF；資料庫記下檔案編號、類別、年級、狀態 | ✅ 存放統一成可替換的 StorageService（本機；Google 雲端硬碟程式已完成、尚未實機） |
| M4 | OCR 辨識 | 上傳後自動辨識出課名、分數、證照名稱、發證單位、日期 | ✅ 本機 RapidOCR 離線辨識（展示站預設示範模式） |
| M5 | 規則檢查 | 分數 0–100、學分合理、課名比對；不合理的欄位標出來 | ✅ 分數 0–100、學分 0–10、課名對照課綱、低信心欄位標示 |
| M6 | 學生確認 | 學生修正辨識結果，按確認後才寫進正式資料 | ✅ |
| M7 | 學習證據 | 確認過的成績、證照、經歷都有固定的證據編號 | ✅ |
| M8 | 有依據的自傳 | 每段自傳標出用了哪幾筆證據；AI 引用不存在的編號會被移除；未確認資料不進自傳 | ✅（AI 為選用） |
| M9 | 導師確認送審版 | 送審時固定一份快照；學生之後再改是下一版，不影響老師看的那份 | ✅ |
| M10 | 刪除與保留 | 學生刪除先標記「已刪除」，不馬上消失；送審過的檔案不能被刪掉 | 🟡 檔案只標記；資料列與送審保護 2026-10-27 補齊中 |
| M11 | 操作紀錄 | 登入、確認、送審、刪除都有紀錄 | 🟡 部分有（2026-10-27 補齊中） |
| M12 | 失敗時能手動 | OCR 或 AI 失敗時，學生可以自己填，主線不卡住 | ✅ 可手動新增課程；AI 不能用時改走固定流程 |
| M13 | 自傳歷史版本 | 學生和導師看得到每一版自傳的時間與內容，可以打開舊版 | ✅ 學生有版本紀錄頁；導師看得到和上次確認版本的差異 |
| M14 | 去識別化 | 送 AI 前，身分證字號、學號、姓名、出生日期、證書總編號、照片都已移除；有測試證明 | ✅ 送 AI 前去掉姓名、學號，有測試；OCR 在本機做 |

**V1 的完成定義**：M1～M14 都打勾，而且用一個假學生帳號在瀏覽器從頭走到尾（上傳 → 導師確認）不需要人幫忙。

## 5. 已拍板的決定（2026-10-15，使用者轉達）

| # | 問題 | 決定 |
|---|---|---|
| D1 | 教師端只做班導？ | **只做班導。** 其他教師關係放 V2。 |
| D2 | 用 Google Drive／Docs，不自己重做？ | **同意。** |
| D3 | 沒有學校管理員權限時怎麼測？ | **先用個人的 Google 雲端硬碟**驗證 API。V1 程式先存本機，串好後換成 Drive。 |
| D4 | 自傳的定位？ | **同意「證據＋學生反思的可追溯草稿」，而且要能看過往的歷史版本。** |
| D5 | OCR／AI 要人工確認？ | **同意。由 AI 把資料抓出來填好欄位，學生只檢查對不對，正確才按確認送出。** AI 不給分、不退件、不判定資格。 |
| D6 | 下一階段先做什麼？ | 先跑通主線：上傳 → OCR → 去識別化 → AI 整理欄位 → 學生確認 → 證據 → 自傳 → 送審。 |
| D7 | OCR 用哪一套？ | **在自己的伺服器上辨識（RapidOCR，離線）。** 因為 D5 要先去識別化才送外部 AI，所以原始圖片不能送到外部服務做 OCR。 |

**名詞說明**
- **證據（Evidence）**：學生已確認過的一筆資料，例如一張證照、一門課的成績、一次競賽。每筆有固定編號（F1、F2…）。
- **可追溯**：自傳每一段都標出「這段是根據哪幾筆證據寫的」，按「查看依據」就能看到那張證照或那門課。
- **歷史版本**：每次儲存或送審都留一版，學生和導師可以回頭看以前的版本。目前送審快照已會存版；**歷史版本列表與比較畫面還要做**（M13）。

## 6. 證照上傳到 AI 的資料流程（以技術士證為例）

```
① 學生上傳證照照片
② 伺服器自己做 OCR（離線）→ 得到整張證照的文字
③ 後端去識別化：把下面這些刪掉
     身分證統一編號（例：A123456789）
     出生日期
     技術士證總編號（例：118-0186204）
     姓名（和學生帳號的姓名比對後刪除）
     學號、照片
④ 只把剩下對備審有用的文字送給外部 AI（學生自己的 API 金鑰）
⑤ AI 整理成欄位，例如：
     證照名稱：電腦軟體應用｜發證單位：勞動部｜級別：乙級｜生效／製發日期：民國115年08月21日
⑥ 學生只檢查欄位對不對，正確 → 按確認 → 寫進正式資料，成為一筆證據
```

**規則**
- 原始照片留在伺服器（之後換成 Drive），**不送給外部 AI**。
- 去識別化用固定規則（身分證字號、日期、編號格式，加上比對學生本人姓名），不靠 AI 判斷什麼該刪。
- 送給 AI 的文字要記錄在操作紀錄裡（只記欄位名稱，不記內容），方便證明沒有送出個資。
- 成績單也走同一套流程：只送課名、學分、分數、學年學期。

## 7. 資安與 AI 底線

1. **能不送 AI 就不送。** 送出前先把姓名、學號、證書號碼、條碼拿掉，只留「證照名稱、發證單位、取得年級」這類欄位。
2. **缺曠、成績明細等敏感資料不送 AI。**
3. **API 金鑰**不寫進資料庫、不存在 session、不顯示在畫面。
4. **學期照片**只有學生本人看得到，不給 AI、不給老師、不進備審。
5. **AI 失敗要能退回手動流程**，不能讓主線卡住。
6. 示範只用合成資料，不用真實學生資料，也不編造學長姐的成功故事。

| V1 不做 | 原因 |
|---|---|
| 自己做線上文件編輯器、試算表、雲端硬碟、Email、行事曆 | Google 已經有成熟的工具 |
| GPU 主機自己跑大型模型 | 使用 Gemini API，模型不在學校主機上跑 |
| 錄取機率預測 | 沒有可靠來源，容易誤導學生 |
| 跨校、多租戶、商業化 | 不在專題範圍內 |
| Sheets 儀表板、Gmail 通知、行事曆同步 | 放 V2 |
