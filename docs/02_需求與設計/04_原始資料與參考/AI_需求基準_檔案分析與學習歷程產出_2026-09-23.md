## 1. 老師已明確要求的核心

系統必須能清楚回答：

```text
學生放入什麼資料
  → 系統如何讀取、整理與引導
  → 最後產出什麼學生可直接使用的結果
```

第一版不可只做手動貼文字、上傳檔案列表、雲端硬碟式保存、首頁視覺或尚未接通的 AI 願景。評審優先檢視已完成、可操作、可展示的功能。

本系統的長期定位仍是五專資管科學生的五年學習歷程；但目前開發優先順序改為先完成一條真正可運作的「檔案輸入 → 分析整理 → 結果產出」流程，再將拼圖、五年地圖與公開首頁接到真實資料。

2026-09-29 需求修正：教師逐份查看作品集與 AI 報告的使用頻率及必要性不足，不再作為教師端唯一核心。P0 學生流程保持不變；P1 改以「教師發布年度行政表單 → 學生下載填寫並電子回傳 → 教師初檢 → 科辦追蹤正式狀態」補上可驗證的日常需求。完整邊界見[行政表單數位化與申請追蹤設計規格](../../99_封存_歷史與待確認/02_舊版規格與規劃/AI_設計規格_行政表單數位化與申請追蹤_2026-09-29.md)。

## 2. 第一版根流程

### 2.1 資料來源與責任分工

| 類別 | 資料 | 提供者 | 第一版處理方式 |
| --- | --- | --- | --- |
| 學生輸入 | 成績單 PDF、圖片或掃描檔 | 學生 | 上傳後擷取科目、成績、學分／狀態；學生確認再納入分析。 |
| 學生輸入 | 證照 PDF 或圖片 | 學生 | 上傳後擷取證照名稱、日期、等級等可辨識欄位；學生確認。 |
| 學生輸入 | 選填的專題、競賽、服務學習或實習資料 | 學生 | 以結構化表單或附件補充，供成果文件生成。 |
| 管理資料 | 課程規劃、必修／選修、領域分類、畢業或補修規則 | 管理者／科辦 | 以版本化規則維護；不可由 AI 自行杜撰。 |
| 管理資料 | 證照認可或抵免規則 | 管理者／科辦 | 僅依已公布且適用年度的規則提示；正式資格由授權人員確認。 |

第一版的關鍵不是保證所有掃描檔都零錯誤辨識，而是要做到：**學生直接上傳檔案、系統產生可校正的結構化資料、學生確認後再產出結果。** 不允許把「使用者自行複製貼上全部內容」當作唯一輸入方式。

### 2.2 處理順序

```text
1. 上傳成績單
   → 擷取或辨識課程資料
   → 顯示可編輯的科目、成績、學分與狀態
   → 學生確認

2. 套用當年度課程規劃
   → 分類通識／專業與能力領域
   → 顯示已修、未修、未通過、可能需補修項目

3. 上傳證照與其他歷程
   → 擷取名稱與日期等欄位
   → 對照管理者維護的類別與規則
   → 讓學生確認分類與佐證

4. 產生個人學習歷程結果
   → 成績與能力摘要
   → 課程／證照／成果的對照
   → 待補資料與下一步引導
   → 自傳草稿與學習／入學計畫草稿
   → 可下載的 Word 文件；PDF 為後續輸出格式
```

### 2.3 成績與學籍標記規則

成績分級區間不可永久寫死。第一版可依展示資料呈現分數區間與及格／不及格分類；實際門檻、學分、必修與補修判定應由管理者依學年度設定。

對於轉入資料的文字標記，系統先採可解釋的規則：

| 成績單標記 | 系統初步狀態 | 不可自行推定的事 |
| --- | --- | --- |
| `抵` | 抵免紀錄，列入「已取得／待規則確認」 | 是否符合本校、該年度及該科的正式採計資格。 |
| `免` | 免修紀錄，列入「已取得／待規則確認」 | 是否可折抵特定學分或畢業門檻。 |
| `補` | 補修紀錄，保留為修課歷程的一部分 | 最終是否通過，仍須看該次有效成績或科辦結論。 |
| 數值成績 | 依管理者設定的級距與及格規則分類 | 跨校課程是否可抵免、學分是否等值。 |

### 2.4 學號與轉入規則

| 情況 | 帳號／學號 | 系統處理 |
| --- | --- | --- |
| 一般在校生 | 使用既有學號作為校內帳號 | 對應既有學生資料。 |
| 校內轉科 | **保留原學號與帳號** | 管理者更新目前科系、班級或學籍狀態；原資料不得斷裂。 |
| 校外轉入 | 取得新的校內學號與帳號 | 建立新學生資料；原校成績單與抵免資料作為其學習歷程附件與審查資料。 |

資料庫應使用不可變的內部 `user_id` 關聯資料；學號是校內帳號與顯示欄位，不應成為唯一的歷程關聯依據。

## 3. 學生可看見的結果

學生在確認輸入資料後，至少要能取得以下結果：

1. **學習歷程摘要**：已修課程、成績表現、可辨識的能力領域與已有證照／成果。
2. **課程與補強清單**：已修、待確認、未通過或可能需要補修的項目；每一項都顯示資料與規則來源。
3. **證照與成果分類**：證照、作品、競賽或服務資料對應到可解釋的能力類別。
4. **下一步引導**：缺哪些附件、哪一項資料尚未確認、下一步可上傳或補充什麼；不能將 AI 猜測包裝成校方正式規定。
5. **文件草稿**：根據學生已確認的資料生成自傳草稿與學習／入學計畫草稿，學生可編輯、保留來源與下載 Word 檔。

系統可以協助整理、摘要與撰寫草稿，但不得保證錄取、直接認定抵免資格、取代教師／科辦審核，或在資料不足時捏造學生經歷。

## 4. 第一版驗收標準

以匿名或假資料完成以下單一情境，才可宣稱第一版核心流程可展示：

```text
學生上傳 1 份成績單 + 1 份證照
管理端已備妥 1 個適用年度的課程規劃／分類規則
→ 系統顯示可確認的擷取欄位
→ 學生確認後獲得課程與證照分類結果
→ 系統產出學習歷程摘要、待補清單、自傳草稿與學習計畫草稿
→ 學生可下載 Word 文件
```

展示時須同時說明：哪些內容來自上傳檔案、哪些來自學年度規則、哪些是 AI 草稿，以及哪些仍待人工確認。

## 5. 階段安排

| 優先級 | 範圍 | 可驗收成果 |
| --- | --- | --- |
| P0：根 | 成績單、證照、課程規劃資料的上傳、確認、分類與文件草稿產出 | 完成第 4 節的一條可操作流程。 |
| P1：行政表單與人工確認 | 教師發布版本化表單、學生電子回傳與補件、科辦跨班進度與正式狀態；既有教師學習歷程回饋為支援功能 | 一份匿名申請可從發布、下載、提交、補件走到正式狀態，AI 失敗不阻塞。 |
| P2：體驗層 | 個人五年地圖、拼圖作品集、下一站聚焦與公開首頁 | 畫面顯示 P0／P1 的真實資料。 |
| Future | 正式校務系統介接、全自動 OCR、進階升學推薦、完整 PDF 輸出 | 需校方資料授權、規則版本及額外驗證。 |

## 6. BMAD 與 Gemini 的工作定位

BMAD Agent 團隊由使用者的 IDE 原生環境執行，並可依使用者 IDE 的設定使用 Gemini 模型。BMAD 可協助需求分析、UI／UX、技術架構、程式、測試與文件分工。

本專案的唯一需求依據仍是已確認的規格與測試證據；不同代理模型產生的建議，必須回寫到正式文件並經測試或人工審核，不能直接視為已完成的功能。

## 7. 下一輪需要取得的資料

1. 一份去識別化的成績單 PDF／圖片（可先使用公開或模擬範例）。
2. 一份資管科適用年度的修業科目表、課程對照表或畢業規則。
3. 一至兩份去識別化證照 PDF／圖片。
4. 老師或科辦確認的第一版 Word 輸出樣式；未提供前，以清楚的學習歷程摘要格式製作。
5. 成績及格門檻、學分與補修判定的適用年度規則；未確認前，展示版只做「待確認」提示，不做正式資格判定。
6. 一份可公開或去識別化的行政空白表單、填寫說明、必備附件及實際角色責任；可優先使用證照／競賽抵免作為匿名示範，但不得自行編造正式資格條件。
