# OCR 開發紀錄

本文件整理 OCR 從需求規劃、本機辨識流程到技術士證專用欄位分析的開發歷程。日期以專案文件、測試紀錄和對話截圖可確認的時間為準；沒有證據的日期不另行推測。使用者證照原圖、姓名與識別號碼不寫入本紀錄。

## 2026-09-23：需求規劃

- 學習歷程核心流程將成績單與證照列為上傳資料，方向是先產生可編輯草稿，再由學生檢查確認。
- 此時 OCR 屬於待完成能力；測試使用的 `fake` provider 只產生空白待確認草稿，不冒充真實辨識，也不把未確認內容寫入正式資料。
- 資料擷取、學生確認、正式紀錄寫入是不同步驟；OCR 不得自行判定學籍、資格或證照真偽。

## 2026-10-08：成績單 OCR 本機流程

### 目標與實作範圍

- 建立本機 Tesseract 與 PaddleOCR 介面，回傳文字、圖片座標及引擎信心資訊；辨識信心不等同正確率。
- 以 Pillow 載入圖片，以 PDFium 逐頁轉換 PDF；限制頁數與像素，對不支援或損毀的檔案回傳明確錯誤。
- 以表格幾何位置配對課程、學分、成績與學期，不單靠 OCR 文字順序；保留 0 學分、重複課名和缺漏欄位，未知版型明確要求人工核對。
- 學生可預覽來源文件並重新分析建立新草稿；新草稿使用版本識別防止舊頁面覆蓋新結果。分析失敗時保留舊草稿，已確認紀錄只在明確確認後更新。
- OCR 僅在本機處理，不把來源文件送至雲端辨識服務。

### 本機驗證

- 建立隔離的 Windows Python 3.12 OCR 環境，安裝 PaddleOCR PP-OCRv5 CPU 模型及 Tesseract 介面；模型第一次使用時需初始化或下載快取。
- 以合成資料及一張本機成績單測試兩種引擎。當時完整單頁 CPU 辨識約 8 分鐘；這是該次硬體與樣本的耗時，並非一般請求的固定時間。
- 初始整合測試紀錄為 182 項通過，另有 2 項既有 migration 測試因測試資料庫缺少 `student_profiles` 而失敗；OCR 工作沒有修改該 migration 問題。
- 樣本沒有逐欄人工標註，因此候選筆數不當作正確率，也不宣稱已達到特定辨識準確度。

## 2026-10-15 至 2026-10-19：技術士證專用辨識

依可確認的對話截圖日期及後續開發紀錄，將一般證照草稿流程擴充為臺灣技術士證欄位核對。此處的「判斷」是文件類型辨識及欄位整理，不包含官方資料庫查驗或真偽認證。

### 欄位與證據

- 辨識職類、級別、技術士證總編號、生效日期、製發日期及發證單位；欄位值須來自 OCR 文字，不以版面位置推測填值。
- 保留每欄原文、圖片位置及信心，未讀到或低信心時標示需要人工確認。
- 生效日期和製發日期分開讀取及顯示，即使樣本上兩者相同也保留兩個欄位；民國日期轉為西元日期後，只有製發日期進入既有證照正式資料欄位。
- 技術士證總編號留在 OCR 草稿核對證據，不新增正式紀錄欄位；重新分析建立新草稿，不覆寫已確認紀錄。
- 依人工核對回饋，畫面使用繁體中文；發證單位「勞動部」的疑似 OCR 誤字會標示核對或顯示人工修正依據。

### 依樣本回饋修正

- 標題與欄位分區放大重讀，改善級別、總編號及底部日期／發證單位的辨識依據。
- 發現 OCR 原文已有「會計事務-資訊」，但職類解析只取第一段中文字。新增失敗案例後修正解析，完整保留為「會計事務－資訊」。
- 發現技術士證路徑先執行整頁 PaddleOCR，再逐欄重讀；低信心欄位還會逐一放大重跑。改為標題可辨識時直接分區處理；PaddleOCR 已讀到文字但信心偏低時保留該證據，不再自動重複放大辨識。沒有文字的結果仍可重讀。
- 使用者回報 Tesseract 對反光護貝樣本沒有可用結果，因此技術士證仍以 PaddleOCR 為主要引擎；未將 Tesseract 低輸出當作成功辨識。
- 以本機樣本直接跑調整後的 PaddleOCR 約 40 秒完成並回傳 14 個文字證據區塊。該次包含模型載入，並未完成瀏覽器上傳的端到端驗收，也不能據此承諾每台電腦的處理時間。

### 測試與限制

- 新增技術士證欄位、缺漏欄位、民國日期、職類連字號、來源座標、低信心及草稿確認流程的回歸測試。
- 2026-10-19 OCR 專項測試：77 passed；專案完整測試：263 passed。
- 反光、底紋、模糊、裁切或低解析仍可能導致錯字；OCR 信心不是正確率，學生仍需對照原圖確認。原圖不加入版本庫。
- 本機 OCR 仍為同步處理。正式部署若有短逾時或多使用者併發需求，應採用背景工作程序及可觀察的處理狀態；PaddleOCR 的 CPU 與模型記憶體負載須依部署硬體另行驗證。
