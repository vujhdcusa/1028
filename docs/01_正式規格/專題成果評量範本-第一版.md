# 專題成果評量範本（第一版）

> 依據《專題審查學習目標與評量對照表》整理。本文件是學習歷程系統的成果要求範本，不是另一套專題行政、場地或公告系統。適用年度必須由科辦確認後啟用。

## 一、共用設計原則

- 專題為小組共用成果；個人學習歷程只連結專題並記錄分工、答詢與個人佐證。
- 系統保存階段繳交版本、共同審查結論、補正項目與完成證據。
- 教師共同討論後，由科主任或科助輸入一筆小組共同結果與評語；不建立評審帳號或個別評分功能。
- AI 只可提示缺件或佐證不足，不能給分、判定通過或取代共同審查。

## 二、共同階段

| 階段 | 目的 | 學生繳交／展示證據 | 系統狀態 |
| --- | --- | --- | --- |
| 期中審查 | 確認問題、範圍、方法與進度 | 初步成果、需求或分析、架構或策略、進度表 | `submitted` → `approved`／`needs_revision`／`rejected` |
| 第一次複評 | 確認核心成果形成 | 可操作系統或營運數據、測試或企劃修訂、展示答詢 | `submitted` → `approved`／`needs_revision`／`rejected` |
| 第二次複評 | 關閉指定缺失 | 評語對照、修正前後差異、最終測試或成果展示 | `submitted` → `approved`／`needs_revision`／`rejected` |

### 狀態說明（與程式一致）

| 狀態值 | 畫面顯示 | 說明 |
| --- | --- | --- |
| `draft` | 草稿 | 學生尚未送出，可繼續修改 |
| `submitted` | 已提交 | 學生已送出，等待共同審查結論 |
| `approved` | 核可 | 共同結論為通過 |
| `needs_revision` | 需要補正 | 共同結論要求修正，並列出補正項目 |
| `rejected` | 退件 | 共同結論為不通過 |

補交修正時不另設 `submitted_v2`、`submitted_v3` 等狀態，而是建立新版本：版本號 `version_no` 加 1，並保留前一版本連結；新版本同樣從 `draft` 開始。

## 三、資訊軟體開發組範本

| 評量面向 | 必要成果／證據 |
| --- | --- |
| 問題與需求 | 核心問題、目標使用者、使用情境、需求與功能對照 |
| 架構與流程 | 功能架構圖、流程圖、資料模型、狀態轉換 |
| 核心功能 | 可實際操作的整合版本與成果連結 |
| 權限與控制 | 角色權限表、輸入限制、異動或修改紀錄 |
| 功能測試 | 正常、異常與整合測試紀錄 |
| 資料呈現 | 能回答管理問題的統計表、圖表或儀表板 |
| 修正證據 | 原評語、問題本質、修正措施、完成證據 |

## 四、商務網站經營組範本

| 評量面向 | 必要成果／證據 |
| --- | --- |
| 顧客與需求 | 目標客群、需求、使用或購買情境 |
| 市場與競爭 | 市場規模資料、至少三項競爭或替代方案 |
| 策略推導 | 環境、SWOT 或理論分析與策略對照 |
| 定價分析 | 成本、競品價格、顧客接受度、利潤估計 |
| 營運成效 | 流量、互動、轉換、訂單、營收或其他 KPI |
| 企劃執行 | 目標、對象、方法、預算、期程與 KPI |
| 成果表達 | 簡報、影片、網站或展示內容；全體組員答詢 |
| 修正證據 | 原評語、問題本質、修正措施、完成證據 |

## 五、共同審查紀錄欄位

| 欄位 | 說明 |
| --- | --- |
| 專題、年度、階段、類型 | 指出何組在何階段接受何種範本檢核 |
| 共同結果 | 核可（`approved`）、需要補正（`needs_revision`）或退件（`rejected`）。「修改後通過」以「需要補正 → 補交新版本 → 核可」的版本紀錄呈現 |
| 整體評語 | 委員會共同整理後的短評 |
| 補正項目 | 對應評量面向的具體缺失與要求 |
| 修正措施與完成證據 | 學生回應的版本、檔案、連結或測試結果 |
| 登錄者與時間 | 科主任或科助的登錄紀錄，不代表個別評審分數 |

## 六、四級判定（供年度範本設定）

| 等級 | 含義 |
| --- | --- |
| 4 | 完全達成：可獨立完成、驗證、解釋並依回饋改善 |
| 3 | 基本達成：核心成果可運作或可執行，僅有少量細節待改善 |
| 2 | 部分達成：缺少整合、測試、資料或解釋，仍需指導 |
| 1 | 未達成：成果未完成、未出席，或修改沒有回應評審問題 |
